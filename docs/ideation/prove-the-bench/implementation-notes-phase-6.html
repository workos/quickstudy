Seed — trials-1 run would become the default run

Context
The spec seeds the n1 run with seedRun({ trials: 1, idSalt: "n1" }). It would share SEED_STARTED_AT with the sweep and get a later ULID, so the export (sorted by started_at desc, then id desc) would list it first, making it the default run and breaking the positional runIds() in e2e.
Decision
Added SeedOptions.startedAt? (finish = start + 1h) and seeded n1 at 2026-07-18, older than the cell-states run. Meta order stays sweep, cell-states, n1; runIds() now returns { sweep, cellStates, n1 } and asserts three runs.
Alternative
Rewrite runIds() to resolve runs by trials; rejected because the n1 run would still become the app's default view.

Seed — idSalt is redundant for uniqueness

Context
The spec's Failure Modes row says idSalt prevents duplicate ids in one DB. seedIdBase already advances a per-db invocation counter with a 1,000,000 ms stride, so a second seedRun already mints distinct ids.
Decision
Kept idSalt as specified, but mixed it into the leading four entropy bytes via a pure FNV-1a hash (the counter lives in the trailing bytes). Unsalted streams, including the sweep, are byte-identical to before, and regen stays deterministic.
Alternative
Add the salt to the time base; rejected because an offset below the stride could overlap the next invocation's stream.

Compare — what "an arm with nothing scored" means

Context
The spec says the notice fires when a compared group has an eval where some arm has scored === 0. countArms never creates a zero entry, and the seeded sweep includes a regression eval that only the docs arms run, so a literal "missing arm" rule fired on the 3-trial sweep.
Decision
An eval counts as shared only when every group member has at least one attempt (any status) on it; the notice fires when such an eval has a member with no completed attempt. The notice also renders only when the run has at least one compared group, since "per-arm counts are listed" is otherwise false. Verified with an ad-hoc check: shared plus nothing scored fires, one-arm-only does not, trials 1 fires the trials sentence, and withheld-only groups show nothing.
Alternative
Treat every dash in a listed row as nothing scored; rejected because it flags suites scoped to one treatment, which were never planned for the other arms.

Diagnosis — report loading and copied Markdown order

Context
The spec says to load the report for clustering, and Error Handling says a missing report falls back to per-eval clusters. loadReport throws on a missing, invalid or offline report. The spec is silent on the copy-all Markdown order.
Decision
A second useAsync wraps loadReport(runId).then(r => r.pairs, () => null), so any failure degrades to null. The view waits for both loads to avoid re-laying out. diagnosisMarkdown still orders by DIAGNOSIS_TARGETS, so copied Markdown can differ from the on-screen cluster order. Cluster headings pluralize ("1 arm", "2 findings") instead of printing "arm(s)".
Alternative
Render clusters immediately with null pairs and re-cluster when the report arrives; rejected because the headings would jump.

Validation — dev-data check and working-tree drift

Context
The spec's validation command bun run ui:dev-data && git diff --quiet -- ui/dev-data assumes the regenerated data is already committed. This phase must leave changes unstaged, so the check cannot pass as written. Separately, a sibling phase's uncommitted change in the same tree (src/manifest.ts, the solution field) is picked up by regen, and its untracked tests/oracle.test.ts currently fails tsc --noEmit.
Decision
Checked determinism instead: regenerated twice and diff -r found no differences. The committed dev-data will include "solution": null in manifests if regenerated with the sibling's change present. Re-run bun run ui:dev-data after both phases land. tsc -p ui passes, and the root pass has no errors outside tests/oracle.test.ts.
Alternative
Stash the sibling's changes to regenerate cleanly; rejected because it would touch another stage's work in progress.
